# Adoption guide for technical decision-makers

This document exists for one purpose: to let a Principal/Staff engineer, engineering manager, or security reviewer evaluate `repo-contract` for adoption at organizational scale without having to reconstruct the picture from `README.md`, `SECURITY.md`, `specs/architecture.md`, and the ADRs scattered across the repository tree. Everything here links back to the primary source it summarizes — nothing here is a new claim.

## What problem this solves

Most repositories enforce quality gates as a loose collection of independent CI steps — a lint job, a test job, a coverage job, each configured, ordered, and reported on separately, usually by whoever set up CI first and never revisited. Two failure modes follow directly from that: a check fails and the log says only `Process completed with exit code 1`, leaving whoever's on the hook to re-run it locally just to find out what actually broke; and a platform team wanting the same bar across twenty repositories ends up copy-pasting YAML, which drifts the moment one repo's copy gets a "quick fix" the others never receive.

`repo-contract` treats a repository's own quality bar as one owned, versioned artifact: a declarative graph of checks, each producing structured `Evidence` (what happened) and a repository-owned `Verdict` (whether that was acceptable), with a mandatory, specific `rationale` for every single outcome — never a bare pass/fail. See [README.md](README.md) for the full pitch and a real example of that evidence in practice.

## Security & threat model

Full detail: [`SECURITY.md`](SECURITY.md). The summary a security reviewer needs:

- **No shell interpretation by default.** A `run` string is tokenized into an executable and its arguments; a `run` array is used as argv verbatim. Neither ever passes through a shell on POSIX — no untrusted value interpolated into `run` can inject a second command, a redirect, or a pipeline. The one unavoidable exception is Windows resolving a `.cmd`/`.bat` shim (how essentially every npm-installed CLI is actually invoked there), handled by `cross-spawn`'s own argument escaping, not by a shell repo-contract itself invokes ([ADR 0003](specs/decisions/0003-cross-platform-command-execution-and-process-cleanup.md)).
- **No ambient capability the caller didn't grant.** Process spawning and environment-variable access are capabilities the _consumer_ supplies (`spawn`/`env` on `defineRepoContract()`'s own config) — repo-contract itself never imports a process-spawning implementation or reads `process.env` ([ADR 0011](specs/decisions/0011-process-spawning-and-ambient-environment-access-are-consumer-supplied-capabilities-not-package-owned.md)).
- **The `init` CLI only scaffolds local files.** Neither it nor the library engine makes network calls or collects telemetry — and the no-network property is enforced by a check in this repository's own contract, not merely documented.
- **Supply-chain posture:** npm's OIDC trusted publishing (no long-lived `NPM_TOKEN`) with provenance attestation, so a consumer can verify a published artifact was built by this repository's own CI, not a maintainer's laptop.

## Versioning, stability, and long-term support

Full detail: [`VERSIONING.md`](VERSIONING.md). The three-tier model — **Stable** (`defineRepoContract`/`runRepoContract`'s signatures, the `Evidence`/`CheckEvidence`/`Verdict` shapes and their execution/phasing invariants, the exported error hierarchy, the `run`-string tokenization contract, `repo-contract/helpers`' exception primitives, and the published `./schema` files' own `$id`s), **Experimental** (`repo-contract/presets` and the `init` CLI's detection table/generated file content — each may still change shape, including breaking, in a minor release before a real feedback cycle has run), and **Private** (everything under `src/execution/`, `src/parsing/`, `src/policy/`, and `src/config/`'s internals — never re-exported, may change at any time) — is what the eventual `1.0` stability promise will cover.

Before `1.0`, any minor release may change a Stable API. While the package is `0.x` a breaking change bumps the minor version and a feature the patch version (the release tooling deflates one level — [VERSIONING.md](VERSIONING.md#pre-10-status) explains how, and why no automation can publish `1.0.0` by itself). Starting at the first `1.0` release, security fixes will be backported to the latest minor release of the previous major version for a minimum of six months after a new major version ships, per [ADR 0015](specs/decisions/0015-security-backport-window.md) — a forward commitment, not yet a proven track record.

`Evidence` and `Verdict` each version independently via their own `version` field, separately from the package's own semver — see VERSIONING.md's "Evidence and Verdict schema versioning" section. This matters specifically because repo-contract's output is meant to be consumed as a CI-interoperability artifact (a dashboard, a stored baseline, a separate tool) that may outlive the package version that produced it.

| Ordering is exactly two primitives — `dependsOn` (a real evidence dependency) and `isolated` (a scheduling barrier) — declaration order is the required topological order, and a genuine scheduling race is fixed by declaring the dependency, never papered over with a retry.                                                                                                                                                                                                                                                             | A flaky-looking check is a real bug to fix at the source, not something a retry loop is allowed to hide.                                                              | [0002](specs/decisions/0002-dependson-and-isolated-are-two-scheduling-primitives.md)                                                 |

## Migrating onto repo-contract

There is no dedicated migration guide yet (unlike `@maverickcer/env-cap` and `data-cap`, which each have several) — repo-contract replaces a loose collection of independent CI steps, not one specific competing tool, so the honest starting point is [`examples/day-one-walkthrough`](examples/day-one-walkthrough/README.md) (adding the contract to a repository with an already-red check) and [`examples/exceptions-walkthrough`](examples/exceptions-walkthrough/README.md) (the governed-waiver flow for a check that can't be fixed immediately). Adoption is incremental by design: `--checks a,b,c` runs a named subset, so a team can wire in one check at a time rather than replacing an entire CI pipeline in one PR.
