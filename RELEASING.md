# Releasing (maintainers)

Maintainer-facing. Contributors don't run any of this — a normal change is just a PR;
a changeset now appears automatically even if you don't add one by hand (see
[`CONTRIBUTING.md`](CONTRIBUTING.md#making-a-change)).

Releases are fully automated by [Changesets](https://github.com/changesets/changesets)
and npm's [OIDC trusted publishing](https://docs.npmjs.com/trusted-publishers), via a
shared, centrally-maintained workflow hosted in
[`internal-package-contract`](https://github.com/MaverickCER/internal-package-contract/blob/main/.github/workflows/release-npm-changesets.yml)
that this repo's own [`.github/workflows/release.yml`](.github/workflows/release.yml)
calls into (`uses:`). **No `NPM_TOKEN` secret exists in this repository** and none is
needed — npm verifies the workflow's OIDC identity against a one-time
trusted-publisher registration on npmjs.com (see [One-time setup](#one-time-setup)
below).

Migrated off [release-please](https://github.com/googleapis/release-please) onto this
shared setup so repo-contract matches data-cap/env-cap exactly, rather than
maintaining a third, bespoke release mechanism — see the "Standardize npm release +
GitHub Pages deploy" plan for the full rationale (the release-please "PR that does
nothing, then a release PR" friction pattern this repo used to hit, among others).

## How releases work

1. Every PR lands with a changeset in `.changeset/` — either hand-written (Markdown,
   `patch`/`minor`/`major` + a consumer-facing description) or generated automatically
   from the commit's own Conventional Commit subject if the PR didn't add one (`feat:`
   → minor, a breaking-change marker → major, everything else → patch as the default;
   see the shared workflow's own comment for the exact rule and its one narrow
   exemption for meta-tooling-only commits). Either way, no PR merges without a
   version-impact record.
2. On each push to `main`, the shared workflow runs `changesets/action`. If any
   unreleased changesets are pending, it opens or updates a pull request titled
   **"Version Packages"** from the branch **`changeset-release/main`**, dispatches
   this repo's own `ci.yml` onto that branch (a `GITHUB_TOKEN`-pushed branch never
   otherwise triggers `push`/`pull_request` workflows), and — once that dispatched
   run comes back green — **merges the PR automatically**. No one has to notice it's
   ready and click merge.
3. That merge triggers the shared workflow again. This time there are no pending
   changesets, so it runs `npm run release` (`changeset publish`), which runs
   `prepublishOnly` (the full `npm run contract` gate) and then publishes to npm over
   OIDC with provenance.
4. The publish also fires a `repository_dispatch` to `internal-package-contract`,
   which automatically opens and auto-merges a PR there bumping its own
   `repo-contract` dependency pin and its own version by the matching severity — see
   [One-time setup](#one-time-setup)'s PAT bootstrap step, without which this one link
   in the chain silently no-ops.

`CHANGELOG.md` is generated by `@changesets/cli/changelog` — never hand-edit it. Fix a
wrong entry by correcting the offending changeset before the "Version Packages" PR
merges, or with a follow-up changeset after. Its pre-migration history (the
release-please era) stays as-is; only future entries render through Changesets.

## API baseline and browsable docs

[`.github/workflows/api-baseline.yml`](.github/workflows/api-baseline.yml) is a thin caller of
[`internal-package-contract`](https://github.com/MaverickCER/internal-package-contract)'s own
reusable `api-baseline-sync.yml` workflow, which regenerates every entry point's own
`.repo-contract/api-contract/<target>/baseline.*` (`index`, `presets`, `helpers`) on the Version
Packages PR branch (`changeset-release/main`), so it lands in the same merge as the version bump.
If that job is ever disabled, run `npm run contract:baseline`
(`internal-package-contract update-baseline`) after the release and commit the result — that is
the only other way the baseline is updated.

The browsable HTML API reference (`docs/api/`) is **no longer tied to the release
cadence** — see the GitHub Pages section below. It is not committed at all anymore; it
regenerates fresh on every push to `main` as part of the Pages deploy.

`runUpdateBaseline` (internal-package-contract's own
`scripts/api-contract/update-baseline.ts`) has four outcomes per target — only the first two
exit 0:

| outcome   | when                                                                                                                                                            | writes? |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------- |
| `updated` | no baseline yet; **or** `package.json`'s version is strictly greater than the baseline's; **or** the version is unchanged but the public API contents differ    | yes     |
| `current` | the baseline already carries `package.json`'s version **and** its contents match                                                                                | no      |
| `refused` | `package.json`'s version is unparseable; **or** older than the baseline's (a would-be regression); **or** the committed baseline records an unparseable version | no      |
| `failed`  | API Extractor reported errors                                                                                                                                   | no      |

`current` is what every re-run of the same Version Packages PR sees (the job's own
baseline commit, `changesets/action` refreshing the PR after a later merge), so the
job stays green. This guardrail's own standing verification now lives in
internal-package-contract's suite (this engine, `api-contract`, moved there — see
`repo-contract.config.ts`'s own module doc comment); the `api-contract` check itself,
run as part of `npm run contract` on every PR here, is what confirms it still behaves
correctly against this repository's own real multi-target baseline, so no manual dry
run is needed before a release.

## GitHub Pages

Deployed via [`actions/deploy-pages`](https://github.com/actions/deploy-pages) (the
modern, artifact-based flow), through a shared reusable workflow hosted in
`internal-package-contract` (`deploy-pages-typedoc.yml`) — the same mechanism
data-cap/env-cap already use. `docs/api/`, the coverage/mutation badge JSON, and the
OpenSSF Scorecard evidence doc are all built fresh on every push to `main`
and handed to the deploy step as build artifacts; **nothing is committed back to the
repo for Pages anymore.** Repo setting: GitHub → Settings → Pages → source is "GitHub
Actions" (not "Deploy from a branch").

`docs/api/` regenerating on every push instead of only at release time is a deliberate
behavior change from before this migration —
[specs/decisions/0008](specs/decisions/0008-self-hosting-tool-and-dependency-choices.md)
documented the old release-cadence-only rationale and has a follow-up amendment
recording this change.

If the `deploy` job is ever disabled, run `npm run docs:api` locally and it will
regenerate `docs/api/` (uncommitted — Pages just won't reflect it until the job runs
again).

## One-time setup

- **Merge style.** No longer constrained by release-please's tag-matching needs —
  squash, merge-commit, or rebase are all fine; `changesets/action`'s own release
  commit is what release automation actually keys off, not the PR's own merge shape.
- **Let Actions open the Version Packages PR.** GitHub → Settings → Actions →
  General → Workflow permissions: tick **"Allow GitHub Actions to create and approve
  pull requests"**. Without it, `changesets/action` cannot open the PR at all.
- **Cross-repo dispatch PAT (`CROSS_REPO_PAT`).** The default `GITHUB_TOKEN` cannot
  dispatch events to a different repository at all, which both the
  `notify-internal-package-contract` job in this repo's own `release.yml` (part E)
  and internal-package-contract's own dispatch-to-dependents step (part F) need. This
  is a **fine-grained PAT**, created once by a maintainer:
  1. On GitHub → Settings → Developer settings → Fine-grained tokens → generate a new
     token scoped to `MaverickCER/internal-package-contract` (and, for part F's own
     bootstrap in that repo, `MaverickCER/data-cap` + `MaverickCER/env-cap`), with
     **Contents: Read and write** and the ability to trigger
     `repository_dispatch` (covered by the same Contents permission).
  2. Add it as a repository secret named `CROSS_REPO_PAT` in **this repo** (for the
     outbound dispatch to internal-package-contract) and, separately, in
     **internal-package-contract's own repo settings** (for its outbound dispatch to
     data-cap/env-cap) — the same PAT value works in both places, but GitHub secrets
     are per-repo, so it has to be added twice.
  3. Until this is bootstrapped, `notify-internal-package-contract` fails harmlessly
     (a job failure on an otherwise-successful release, not a blocked publish) — fix
     it whenever convenient; nothing about the npm publish path depends on it.
- **npm trusted publishing.** Already registered from before this migration — no
  change needed. Registration on npmjs.com is keyed to `workflow: release.yml` in
  this repo, which doesn't change; only the workflow's own internals do.

## Recovering from a failed release

Same recovery playbook as any other Changesets-based consumer in this org — see
env-cap's or data-cap's own `RELEASING.md` "Recovering from a failed release" section
for the general cases (PR open but nothing published; PR merged but publish failed;
published but a trailing step failed; wrong version published). Nothing about this
repo's recovery differs from theirs now that it uses the identical shared workflow.
