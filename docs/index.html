    Engineering standards, made executable

    Turn your repository's engineering standards into enforceable contracts.

    Your linters, test runners, security scanners, type checkers, and other tools already produce results. The missing piece is the contract that says what those results mean for your repository.

    repo-contract executes the checks you configure, captures what actually happened as structured evidence, and hands that evidence to policies your repository owns. Your tools produce the facts. Your repository decides what those facts mean.

    • Configure any command as a check — no plugin API to learn.
    • Run checks concurrently, with explicit ordering and isolation when needed.
    • Capture exit code, signal, timing, and output as structured evidence.
    • Decide pass, fail, or warn with a policy function you own.
    • Run the exact same gate locally and in CI — no drift.
    • No CLI, no network calls, no telemetry, no hidden state.

    The problem

    Your repository has standards. Your automation has commands. The contract between them is usually scattered.

    A mature repository may enforce dozens of engineering requirements: tests must pass, coverage must remain above a threshold, public APIs must remain compatible, dependency vulnerabilities must be absent, mutation scores must meet a target, architecture boundaries must hold, and documentation must stay synchronized.

    • The checks themselves live in different tools, each with its own output and failure semantics.
    • The meaning of those results is frequently encoded across CI YAML, shell scripts, package scripts, and tool-specific configuration.
    • Cross-check requirements become workflow conditions and ad hoc glue instead of repository-owned policy.
    • CI becomes responsible not only for executing standards, but for defining what the standards actually are.
    • Local reproduction becomes a matter of reproducing CI's implementation rather than simply executing the repository's contract.

    The missing layer

    Repositories need a layer between "run these tools" and "what does this mean?" That layer should capture execution as fact, apply repository-owned policy to those facts, and return a structured result that another system can enforce.

    repo-contract is that layer.

    The contract

    Your CI system should execute your engineering standards, not define them.

    GitHub Actions, GitLab CI, CircleCI, or another automation platform can execute a contract. ESLint, Vitest, Playwright, Stryker, npm audit, and other tools can produce the evidence. repo-contract connects those pieces without becoming the tool that defines quality for you.

    The repository defines an engineering contract. repo-contract executes configured checks, assembles evidence, evaluates repository-owned policies, and produces a verdict. Local scripts and CI systems consume that verdict.

    1. Your repository
      1. Defines what must be checked
      2. Defines what evidence matters
      3. Defines what constitutes pass, warn, or fail
    2. repo-contract
      1. Executes the configured checks
      2. Captures structured evidence
      3. Evaluates repository-owned policies
      4. Produces one verdict
    3. Local or CI automation
      1. Runs the same contract
      2. Consumes the evidence and verdict
      3. Decides what action to take

    The distinction matters: repo-contract is not another CI provider, test runner, linter, or static-analysis platform. It is the contract runtime that lets those existing tools participate in a repository-owned engineering standard.

    The simplest mental model

    Your tools produce results. Your repository decides what those results mean.

    repo-contract makes that decision executable, inspectable, and reusable.

    The pipeline

    Five stages, strictly in order, every run

    A contract has one execution model: configure what to run, execute it, assemble what happened into evidence, apply repository-owned policy, and aggregate the results into a verdict.

    The repo-contract pipeline progresses from configuring checks, executing them, assembling evidence, evaluating policy, and aggregating a verdict.

    1. Configure
      1. A command per check
      2. Optional output parsing
      3. A policy function you write
    2. Execute
      1. No shell by default
      2. Bounded concurrency
      3. dependsOn / isolated ordering
    3. Evidence
      1. Exit code, signal, timing
      2. Captured stdout/stderr
      3. Parsed output, if requested
    4. Policy
      1. Runs after all evidence exists
      2. Can read every sibling check
      3. Returns pass, fail, or warn
    5. Verdict
      1. One outcome per check
      2. A mandatory rationale
      3. Aggregated pass/fail

    repo-contract deliberately keeps execution and policy evaluation separate. Every check's evidence is fully assembled before policies run. That makes cross-check policy deterministic by construction rather than dependent on timing or CI-specific orchestration behavior.

    The contract boundary

    Configuration and policy belong to the repository. Execution, evidence assembly, and verdict aggregation belong to repo-contract.

    01 · Configure

    A check is a command, optional output parsing, and a policy

    There is no plugin API to learn and no requirement to replace the tools your repository already uses. A check is the command you would already run from a terminal, plus the policy that defines what its result means.

    repo-contract.config.ts 
    checks: {
  lint: {
    run: ["eslint", ".", "--format", "json"],
    output: { format: "json" },
    policy: ({ result }) => {
      if (!result.output?.success) {
        return { outcome: "fail", rationale: "eslint output was not valid JSON." }
      }

      const files = result.output.value as { errorCount: number }[]
      const errors = files.reduce((sum, file) => sum + file.errorCount, 0)

      return errors === 0
        ? { outcome: "pass", rationale: "eslint reported 0 errors." }
        : { outcome: "fail", rationale: `${errors} lint error(s).` }
    },
  },
}

    A published, Experimental preset catalog can provide ready-made configurations for common tools while keeping the final configuration in your repository. Presets are conveniences; the contract remains yours to inspect and override.

    02 · Execute

    Run existing tools without turning your contract into shell glue

    A run string is tokenized into an executable and its arguments without invoking a shell by default. Checks run independently and in parallel unless the contract explicitly requires ordering or isolation.

    ordering two checks 
    checks: {
  build: {
    run: "npm run build",
    policy: ({ result }) =>
      result.exitCode === 0
        ? { outcome: "pass", rationale: "Build succeeded." }
        : { outcome: "fail", rationale: "Build failed." },
  },

  integration: {
    run: "npm run test:integration",
    dependsOn: ["build"],
    policy: ({ result }) =>
      result.exitCode === 0
        ? { outcome: "pass", rationale: "Integration tests passed." }
        : { outcome: "fail", rationale: "Integration tests failed." },
  },
}
    • dependsOn is ordering only.

      A dependency's policy result is never silently used to decide whether a dependent spawns. The dependent receives evidence and its own policy determines what that evidence means.

    • isolated is exclusivity, not a dependency.

      A check whose tooling needs exclusive access to the machine can request isolation without manually naming every other check.

    • A timeout or abort kills the whole process tree.

      Wrapper commands frequently spawn child processes. Cleanup therefore targets the process tree across supported platforms, including Windows.

    Proof in the repository

    The tokenizer, concurrency pool, and dependency scheduler are real, independently tested modules rather than conceptual abstractions.

    03 · Evidence

    Capture what happened before deciding what it means

    Evidence describes execution without deciding whether that execution was acceptable. It records the facts a repository policy can reason about.

    one check's evidence 
    {
  command: "eslint",
  args: [".", "--format", "json"],
  exitCode: 1,
  signal: null,
  stdout: "...",
  stderr: "",
  status: "completed", // | "timed_out" | "signaled" | "host_terminated" | "spawn_error" | "aborted"
  output: { format: "json", success: true, value: [ /* parsed */ ] },
}

    status describes why a process ended. A non-zero exit code can still have status: "completed"; a timeout remains a timeout even when the policy ultimately treats it as failure. Evidence does not have to agree with the policy.

    Evidence is a fact layer

    The same evidence can support different repository policies. A repository may treat a non-zero exit code as failure, while another policy may intentionally interpret parsed output differently.

    04 · Policy

    Your repository decides what the evidence means

    Policy is where engineering standards become executable. repo-contract does not prescribe coverage thresholds, lint severity, mutation scores, security tolerances, or other definitions of quality. Your repository does.

    a policy reading a sibling check 
    policy: ({ result, evidence }) => {
  const testsPassed = evidence.checks.tests?.exitCode === 0

  if (!testsPassed) {
    return {
      outcome: "fail",
      rationale: "Mutation testing requires a passing test suite.",
    }
  }

  const score = Number(result.stdout)

  return score >= 90
    ? { outcome: "pass", rationale: `Mutation score was ${score}%.` }
    : { outcome: "fail", rationale: "Mutation score was below the 90% requirement." }
}
    • Every policy runs, for every check, every time.

      repo-contract does not silently reinterpret a timeout, signal, spawn error, or non-zero exit code as a policy decision.

    • A policy that throws is a bug, not a failing check.

      A policy error rejects runRepoContract() distinctly from a policy that successfully returns { outcome: "fail" }.

    The repository owns the standard

    repo-contract supplies the execution and evidence model. It does not impose its own definition of "good code" on the repository using it.

    05 · Verdict

    One structured answer, with a rationale you can act on

    Every check produces a policy result. Those results aggregate into one Verdict that another system can consume without parsing CI logs or rerunning the tools.

    reading the result 
    const { evidence, verdict } = await runRepoContract(config)

console.log(verdict.passed) // true | false
console.log(verdict.checks.lint) // { outcome: "fail", rationale: "3 lint error(s)." }

process.exitCode = verdict.passed ? 0 : 1

    rationale is mandatory for every outcome, including "pass". It is a plain, JSON-serializable string rather than a tool-specific report shape, so the verdict can be persisted, transmitted, inspected, or consumed by another program.

    The caller remains in control

    runRepoContract() does not call process.exit(). A local script, CI job, release system, or another consumer decides what action to take from the returned evidence and verdict.

    Three questions, three answers

    Evidence, policy, and enforcement stay separate on purpose

    A reliable engineering contract should distinguish what happened from what the repository concluded and what an external system ultimately does about that conclusion.

    Evidence answers what happened. Policy answers what the repository concludes. Consumer judgment answers what an external system does about that conclusion.

    1. Evidence answers "what happened?"
      1. Exit code, signal, timing
      2. Captured and parsed output
      3. Facts without policy interpretation
    2. Policy answers "what does our standard require?"
      1. Repository-owned judgment
      2. Pass, fail, or warn
      3. A mandatory rationale
    3. The consumer answers "what do we do about it?"
      1. CI can block a merge
      2. A script can set an exit code
      3. A bot or human can inspect the result

    Verdict is returned alongside Evidence, never merged into it. A consumer therefore has both evidence.checks[id] and verdict.checks[id] available independently.

    The contract is not the automation platform

    A CI provider can enforce the verdict. It does not have to own the definition of the standard that produced it.

    Why repo-contract

    Keep the tools. Keep the CI. Move the contract into the repository.

    repo-contract does not replace the tools that analyze your code or the systems that automate your repository. It gives those systems a common, repository-owned contract to execute.

    Architecture

    A deliberately small runtime around a strict contract boundary

    The public API exposes only what consumers need to define and execute a contract. Internal modules remain separate so execution, evidence assembly, and policy evaluation cannot silently collapse into one implementation concern.

    The public barrel exports defineRepoContract and runRepoContract. Internally, config validation, execution, evidence assembly, and policy evaluation remain separate modules composed by run-repo-contract.ts.

    1. src/index.ts — public barrel
      1. config/
        1. Tokenize run
        2. Validate configuration structure
      2. execution/
        1. Spawn, timeout, abort
        2. Concurrency and dependency scheduling
        3. Process-tree cleanup
      3. evidence/
        1. Attach parsed output
        2. Assemble the versioned evidence object
      4. policy/
        1. Invoke every policy
        2. Aggregate the verdict
      5. presets/
        1. Independent public barrel
        2. Published under ./presets

    src/presets/ is deliberately independent from the root barrel. The core API and the Experimental preset catalog therefore have separate public boundaries and compatibility expectations.

    Proof in the repository

    The module-boundary map and reasoning behind the architectural decisions are committed documentation rather than conventions that consumers have to infer.

    FAQ

    Common questions about repo-contract

    What problem does repo-contract solve?

    Repositories accumulate engineering standards across linting, testing, security, architecture, API compatibility, coverage, documentation, and other concerns. The tools that implement those checks are usually excellent at producing results, but the repository's rules about how those results should be interpreted often end up scattered across CI workflows and scripts.

    repo-contract provides the layer between those tools and the automation that enforces them: execute checks, capture evidence, apply repository-owned policies, and produce a structured verdict.

    Is repo-contract a CI provider?

    No. Keep your existing CI provider. GitHub Actions, GitLab CI, CircleCI, or another automation system can execute the contract. repo-contract is the repository-owned contract runtime underneath that automation.

    Is repo-contract a test runner, linter, or static-analysis tool?

    No. It does not attempt to replace specialized engineering tools. It executes the commands your repository already trusts and provides the evidence and policy layer around their results.

    Why not just use GitHub Actions or another CI system?

    You should use your existing CI system. The distinction is ownership: CI should execute the repository's engineering contract rather than become the place where that contract is defined.

    repo-contract lets the same contract run locally and in CI while keeping its execution semantics, evidence model, and policy in repository-owned code.

    Why not just use npm scripts, Make, or shell scripts?

    Those tools are useful for command orchestration and can reproduce much of what repo-contract does. repo-contract adds a defined evidence model, explicit policy functions, cross-check access, structured rationales, and an aggregated verdict.

    The value is not that arbitrary command execution is impossible without repo-contract. The value is having a reusable, typed, tested contract model instead of rebuilding that infrastructure in every repository.

    Does repo-contract replace SonarQube, Qodana, or similar quality platforms?

    No. Those systems provide analysis capabilities and quality models of their own. repo-contract can run them as checks when their results are part of your repository's engineering contract.

    Does repo-contract decide what counts as good code?

    No, by design. It does not impose built-in coverage thresholds, lint tolerances, mutation-score requirements, or other definitions of quality. Those decisions belong to repository-owned policy functions.

    Can a policy read another check's evidence?

    Yes. Every configured check's evidence is fully assembled before any policy runs. Execution and policy evaluation are strictly sequential phases, so policies can safely read sibling evidence without race conditions caused by checks still being executed.

    Does repo-contract persist evidence or maintain a baseline?

    No. It does not maintain a baseline or persist evidence on your behalf. If your repository wants regression detection, it can persist evidence and compare it inside its own policy.

    What happens if my policy throws an error?

    A policy exception is treated as an error in the contract itself rather than as a normal failing outcome. runRepoContract() rejects with a dedicated error, distinct from a policy that successfully returns a failing outcome.

    What does "warn" mean?

    "warn" represents a policy that is satisfied but wants to surface additional information. It does not fail the aggregate verdict and is not intended to be a softer representation of failure.

    Does repo-contract run checks in parallel?

    Yes, by default, within the configured concurrency boundary. Checks that require ordering can declare dependsOn. Checks whose tooling needs exclusive access can declare isolated.

    Does repo-contract work on Windows?

    Yes. Windows command resolution and process-tree cleanup are handled explicitly and tested on a real Windows CI runner.

    Does the repo-contract repository use repo-contract itself?

    Yes. The repository's own contract configures the checks used to validate the project, using the package's public API rather than a special internal execution path.

    Is the website itself checked?

    Yes. The page participates in the repository's verification suite, including accessibility verification against the built page.

    Is repo-contract production-ready today?

    It is pre-1.0. Minor versions may still include breaking changes to the Stable tier before 1.0. The versioning policy documents exactly what is covered by the current compatibility guarantees.

    Does repo-contract sandbox or restrict commands?

    No. It does not sandbox, restrict, or review commands configured by the repository. Command execution is a security-sensitive boundary controlled by the configuration owner. See the security model for the complete threat model and execution rules.

    Where can I read the detailed architecture?

    The architecture specification and Architecture Decision Records contain the full reasoning behind the package's structural choices and execution guarantees.

    Getting started

    Define one requirement. Run the contract.

    No config-file discovery, no separate CLI to learn, and no replacement for your existing tools. Define the contract, call one function, and decide what your automation should do with the result.

    repo-contract.config.ts 
    import { defineRepoContract } from "repo-contract"

export default defineRepoContract({
  checks: {
    tests: {
      run: "npm test",
      policy: ({ result }) =>
        result.exitCode === 0
          ? { outcome: "pass", rationale: "Tests exited 0." }
          : { outcome: "fail", rationale: "Tests must pass." },
    },
  },
})
    run it 
    import { runRepoContract } from "repo-contract"
import config from "./repo-contract.config.js"

const { verdict } = await runRepoContract(config)

console.log(verdict.passed)
process.exitCode = verdict.passed ? 0 : 1

    npm install --save-dev repo-contract — requires Node.js >=20.0.0. No config-file discovery magic and no hidden state.
