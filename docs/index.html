Engineering standards, made executable

Define your engineering standards once. Share them across repositories. Get actionable rationale for every outcome.

Your linters, test runners and security scanners can tell you what happened. They don't define what your organization considers acceptable.

repo-contract is that missing layer: one typed, versioned contract that runs the tools you already use, evaluates their results against policy your repository owns, and returns one verdict, locally and in CI.

Give every repository a consistent, versioned engineering standard without forcing every team to adopt the same tools or migrate its CI.

Pre-1.0 · v0.11.2 · MIT

Quick start 
npm install --save-dev repo-contract tsx
npx repo-contract init
npm run contract

For a project that already has its tools, such as typescript, vitest and eslint. repo-contract bundles none of them; init wires up only the ones it finds in your package.json.

Why it exists

Your engineering standard is probably scattered.

A mature repository enforces dozens of requirements: tests, coverage, public-API compatibility, dependency vulnerabilities, mutation score, architecture boundaries, documentation. The tools that check them are excellent. The rules about what their results should mean end up spread across places no single tool owns.

Where the rules live today: CI YAML, package.json scripts, ESLint / tool configuration, test & release scripts, security workflows, code-review habits — no single place answers: what does "acceptable" mean here?

  1. Where the rules live today
    1. CI YAML
    2. package.json scripts
    3. ESLint / tool configuration
    4. test & release scripts
    5. security workflows
    6. code-review habits
  2. → no single place answers: what does "acceptable" mean here?

Individual tools answer individual questions. Your engineering standard is the answer to all of them together.

How it works

Your tools produce results. Your repository decides what they mean.

A check runs a command. Evidence records what happened: exit code, timing, captured and parsed output. A policy you write decides whether that evidence meets your standard, and can read any other check's evidence to do it. The verdict aggregates every policy result, with a mandatory rationale on each.

ESLint, Vitest, TypeScript, Stryker, npm audit, and any custom checks feed into repo-contract, which captures their results as evidence, applies repository-owned policy, and produces one verdict that local scripts and CI consume.

  1. ESLint · Vitest · tsc · Stryker · npm audit · your own checks
  2. ↓ repo-contract
  3. Evidence → Policy → Verdict
  4. ↓ consumed by a pre-commit hook and CI

Execution and policy evaluation are strictly separate phases: every check finishes and its evidence is assembled before any policy runs, so a policy that reads a sibling check is never a race. That is what lets one decision rest on several results. Verdict is returned alongside Evidence, never merged into it. The API reference has the exact shape of each.

See it

One decision from several checks, with the reason.

The real output of examples/release-gate: three published presets run against one deliberately imperfect file, and a release check whose policy reads their evidence to decide whether a release is permitted.

npm run demo 
[PASS] typecheck
  tsc reported no type errors.

[FAIL] format
  Prettier reported formatting failures:
  Checking formatting...
  [warn] src/greet.ts
  [warn] Code style issues found in the above file. Run Prettier with --write to fix.

[WARN] lint
  ESLint reported 0 errors but 1 warning(s):
  - src/greet.ts:15:3 [no-console]: Unexpected console statement.

[FAIL] release
  Release blocked by format. Passing: typecheck. lint: 0 error(s), 1 warning(s); warnings do not block a release.

Source: examples/release-gate

release runs no command of its own. Its policy reads the evidence of the other three checks and says which one blocks the release, what passed, and what was only a warning. warn does not block the run; fail does. The rationale is a plain string, so a person, a bot or a log can use it equally.

What is guaranteed, and where it stops.

No network calls in repo-contract's own code.Scope: Enforced by an ESLint rule and an independent static scan of the shipped surface, including every preset's spawned command against a reviewed allowlist. Why not just CI

CI distributes how checks run. repo-contract distributes what your organization considers acceptable.

Keep your CI. Shared ESLint configs, reusable workflows and template repositories all distribute individual checks. repo-contract distributes the whole standard (the checks, the policies that relate them, and the rationale for their outcomes) as one versioned package.

Where common approaches stop and repo-contract begins
Today With repo-contract
Rules scattered across workflows and scripts One repository-owned contract
Individual checks Checks, the relationships between them, and their policies
CI-specific orchestration logic The same contract, run locally and in CI
Exit codes and CI job state Structured evidence with a stable, versioned shape
"CI failed" An actionable rationale on every outcome, including pass
Each repository reinvents the glue One shared contract package, inherited

Adoption

Start with one check. Scale when you are ready.

repo-contract is intentionally incremental. Keep your CI provider, linters, test runners and security tools, and introduce the contract around the checks that matter first.

A progressive rollout, not a migration

  1. Wrap one existing check. npx repo-contract init detects what is already in your package.json and generates a starting point.
  2. Write its policy, then run the contract locally and in CI.
  3. Move the next standard into the contract.
  4. Share it across repositories once more than one needs it: an internal package wraps repo-contract and owns the executors, every project of that type extends it, and changes arrive through normal dependency updates.
  5. Introduce a new shared requirement as a dated warn that becomes a fail on a chosen date, so nobody's build breaks overnight. The day-one walkthrough is a runnable example.

You probably don't need it when

npm test and a linter are the whole story, each CI check is already independent and that is fine, and you don't need any policy logic on top of exit codes.
