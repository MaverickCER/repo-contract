Engineering standards, made executable

Define your engineering standards once. Share them across repositories. Get actionable rationale for every outcome.

Your linters, test runners, security scanners, and CI can tell you what happened. They don't define what your organization considers acceptable.

repo-contract turns that missing layer into one typed, versioned contract: it runs the tools you already use, evaluates their results against policy your repository owns, and returns one verdict — the same contract, locally and in CI. You replace none of your existing tools.

Quick start 
npm install --save-dev repo-contract tsx typescript vitest eslint
npx repo-contract init
npm run contract

Why it exists

Your engineering standard is probably scattered.

A mature repository enforces dozens of requirements — tests, coverage, public-API compatibility, dependency vulnerabilities, mutation score, architecture boundaries, documentation. The tools that check them are excellent. The rules about what their results should mean end up spread across places no single tool owns.

Engineering rules today live scattered across CI YAML, package.json scripts, ESLint and other tool configuration, test and release scripts, security workflows, and code review habits — leaving no single place that answers what "acceptable" means for the repository.

  1. Where the rules live today
    1. CI YAML
    2. package.json scripts
    3. ESLint / tool configuration
    4. test & release scripts
    5. security workflows
    6. code-review habits
  2. → no single place answers: what does "acceptable" mean here?

Individual tools answer individual questions. Your engineering standard is the answer to all of them together.

How it works

Your tools produce results. Your repository decides what they mean.

A check runs a command. Evidence records what happened — exit code, timing, captured and parsed output. A policy you write decides whether that evidence meets your standard, and can read any other check's evidence to do it. The verdict aggregates every policy result, with a mandatory rationale on each.

ESLint, Vitest, TypeScript, Stryker, npm audit, and any custom checks feed into repo-contract, which captures their results as evidence, applies repository-owned policy, and produces one verdict that local scripts and CI consume.

  1. ESLint · Vitest · tsc · Stryker · npm audit · your own checks
  2. ↓ repo-contract
  3. Evidence → Policy → Verdict
  4. ↓ consumed by a pre-commit hook and CI

Execution and policy evaluation are strictly separate phases: every check finishes and its evidence is assembled before any policy runs, so a policy reading a sibling check is never a race. Verdict is returned alongside Evidence, never merged into it — the caller weighs both.

Why CI isn't enough on its own

CI distributes how checks run. repo-contract distributes what your organization considers acceptable.

Keep your CI. Shared ESLint configs, reusable workflows, and template repositories all distribute individual checks. repo-contract distributes the whole standard — the checks, the policies that relate them, and the rationale for their outcomes — as one versioned package.

Where common approaches stop and repo-contract begins
Today With repo-contract
Rules scattered across workflows and scripts One repository-owned contract
Individual checks Checks, the relationships between them, and their policies
CI-specific orchestration logic The same contract, run locally and in CI
Exit codes and CI job state Structured evidence with a stable, versioned shape
"CI failed" An actionable rationale on every outcome, including pass
Each repository reinvents the glue One shared contract package, inherited

The organizational payoff

Define the standard once. Share it across repositories.

An organization expresses its engineering standard for a project type once — as an internal package that wraps repo-contract and owns the executors. Every project of that type extends it rather than redefining it, and picks up changes through normal dependency updates.

An organization defines its engineering standard once as a shared contract package. Every service consumes that same package and runs the identical contract, both locally and in CI.

  1. Engineering standard → shared contract package
    1. Service A — the same contract, locally and in CI
    2. Service B — the same contract, locally and in CI
    3. Service C — the same contract, locally and in CI

Not a way to break 200 repositories overnight

A new shared requirement can land as a dated warn — visible everywhere on day one, blocking nobody — and become a fail on a chosen date. The day-one walkthrough is a runnable example of exactly that.

See it

Not just "CI failed."

The real output of the tiny contract in examples/demo — three published presets against one deliberately imperfect file:

npm run demo 
[PASS] typecheck
  tsc reported no type errors.

[FAIL] format
  Prettier reported formatting failures:
  Checking formatting...
  [warn] src/greet.ts
  [warn] Code style issues found in the above file. Run Prettier with --write to fix.

[WARN] lint
  ESLint reported 0 errors but 1 warning(s):
  - src/greet.ts:15:3 [no-console]: Unexpected console statement.

Every line says what happened, where, why the repository treats it that way, and — when there is something to fix — how. warn does not block the run; fail does. That rationale is a plain, JSON-serializable string, so it can be persisted, diffed, or consumed by a bot as readily as by a person.

Adoption

Don't replace your stack. Put a contract around it.

repo-contract is intentionally incremental. Keep your CI provider, linters, test runners, and security tools. Introduce the contract around the checks that matter first.

A progressive rollout, not a migration

  1. Wrap one existing check — npx repo-contract init detects what's already in your package.json and generates a starting point.
  2. Write its policy.
  3. Run the contract locally.
  4. Run the same contract in CI.
  5. Move the next standard into the contract.
  6. Share the contract across repositories, once more than one needs it.

Proof, not promises

repo-contract uses repo-contract.

The project is self-hosted: its own repository defines a contract with the public API and uses that contract to validate itself. The implementation, tests, architecture documentation, and decision records are the evidence behind everything on this page.
