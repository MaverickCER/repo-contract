repo-contract: a one-page brief

repo-contract lets every repository follow one shared, versioned engineering standard, and explains every decision it makes.

The problem

Each team keeps its quality rules in different places, so nobody can say what "acceptable" means across the organization. New requirements are hard to introduce without breaking people's builds.

What it does

It runs the checks a team already has, such as tests, linting and security scans. It then applies one agreed standard to their results and gives a single verdict, with a plain-language reason, on a developer's machine and in CI.

Why it matters

  • Every team is held to the same written-down standard.
  • A new requirement can start as a warning with a date and later become a blocker, so nobody is surprised.
  • Exceptions can be recorded with a reason instead of living in someone's memory.

What it costs

Adopting it in one repository is a small change: install the package, run a generator and keep the existing tools. It replaces none of them, and it is free, open source software under the MIT licence.

What could go wrong

  • repo-contract is pre-1.0. A 0.x minor may carry a breaking change to the Stable tier before 1.0, so pin the version and read the changelog on every minor upgrade.
  • The standard is only as good as the policies a team writes. The package enforces what you define; it does not decide what is good.
  • It sees only what a check measures, so it does not replace judgement in code review.

What we are asking for

Agree that one repository trials it for a few weeks, then judge from the results whether to share a standard across teams.
